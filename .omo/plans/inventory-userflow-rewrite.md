# inventory-userflow-rewrite - Work Plan

## TL;DR (For humans)
- **What you'll get**: rewrite besar user flow inventaris warung (login PIN + nama toko → dashboard 3-tab → SKU 1-halaman-lengkap → in-out kasir FEFO → statistik 14-hari + omzet → Telegram rekap 07:00 ala manajer + saran AI bebas-promo) dengan backend Dexie yang sudah ada akhirnya dicolok ke UI real (FakeRepository pensiun).
- **Why this approach**: big-bang dipecah 8 wave / 27 task berurutan, tiap task = 1 branch `feat/*` + 1 PR GitHub + 1 reviewer + CI hijau + squash (hormati AGENTS.md GitHub Flow + permintaan user). Docs direvisi dulu (Wave 0) supaya Schrodinger Must-NOT (Telegram real-send, scan kamera) tidak menggagalkan gate.
- **What it will NOT do**: tidak ada backend/Supabase/Firebase; tidak ada multi-user/role; tidak ada POS cart/checkout/payment; tidak ada chart berat selain grafik mini arus; tidak ada OCR; token bot Telegram tidak pernah plaintext di git.
- **Effort**: 27 implementation todos + 4 final verifiers, 8 wave berurutan (schema → auth → SKU → inout → expiry → dashboard → setting).
- **Risk**: migrasi Dexie v2 (kode/tags/transaksis) + HPP timpa + prefix ikut-ubah; mitigasi: backfill test + hpp_history arsip + tiap wave PR terpisah bisa revert per-wave.
- **Decisions (28 butir user-owned)**: PIN + nama toko offline-first • dashboard SKU+kritis+mini-stat + tombol ikon • setting backup+PIN+profil, threshold di bawah • SKU plus barcode manual+kamera (lib html5-qrcode lazy) • pisah kategori vs tag • kode prefix 3-huruf kapital, backfill otomatis, prefix ikut nama baru via migrasi transaksional • detail SKU + grafik mini SVG arus (marker BEP hijau #16a34a) • form in-out lengkap + catatan, semua barang jualan, FEFO, HPP timpa + simpan riwayat • statistik rank + histori + omzet 14 hari (omzet = jual×qty, margin = omzet−HPP terjual, cashflow = omzet−belanja 14d) • kritis = days <= max threshold kategori, input tanggal/durasi • Telegram owner/manajer, token enkripsi + antre retry 3x (5s/30s/5m) dedup batchId+tanggal, rekap 07:00 + cashflow • AI bebas jenis promo + floor per-jenis, user pilih dulu + tombol AI • dashboard hanya kritis + halaman khusus → detail SKU • 3 tab + sub-tab • big-bang via wave-PR + rebase tiap task • tests-after • tiap task PR GitHub.

## Scope
IN:
- Wave 0: ADR-003 Telegram + amandemen Must-NOT (kamera/scan), revisi FRD-02/03/05/06 + CONTEXT + AGENTS guardrail, HUMAN.md untuk token bot.
- Wave 1: Dexie v2 (skus.kode unik per org, tags + sku_tags, transaksis: jenis/harga_jual_snapshot/pengirim/penerima/catatan, hpp_history), helper consumeFEFO/computeKode, backfill kode.
- Wave 2: LoginPage PIN + nama toko, lockout, guard sebelum dashboard.
- Wave 3: SKU katalog real, form create + barcode manual, scan kamera lazy-route, tag CRUD, detail 1-halaman + grafik mini arus 14d.
- Wave 4: In-out sub-tab SKU, form 7-field tanggal/durasi, FEFO consume, HPP timpa + riwayat, transaksis write.
- Wave 5: Kritis ikut threshold kategori, halaman khusus kritis → detail SKU, Telegram adapter enkripsi + antre, scheduler 07:00 + on-open + on-insert, AI assist multi-jenis promo + guardrail per-jenis, approve flow.
- Wave 6: Dashboard real (pensiun FakeRepository/seedMode), 3-tab + sub-tab Statistik (rank, kecepatan, histori, omzet/margin 14d), empty states.
- Wave 7: Setting (backup+PIN+profil+threshold bawah), wiring notifScheduler, build/PWA/gate hijau, sync docs.
OUT / Must-NOT-Have:
- Must NOT tambah backend, Supabase, Firebase, multi-role, POS cart, payment.
- Must NOT OCR/QR dalam bentuk apa pun — allowlist kamera HANYA untuk barcode scan via lib literal todo 10.
- Must NOT biarkan LLM hitung angka (harga/HPP/omzet/cashflow/BEP) — angka dari engine deterministik, LLM hanya wording + pairing.
- Must NOT ubah daysToExpiry dari Asia/Jakarta startOfDay + ceil.
- Must NOT commit token/plaintext secret (Telegram/Gemini) — enkripsi PBKDF2+AES-GCM via src/lib/crypto.ts.
- Must NOT auto-activate promo — selalu proposed → approve manual.
- Must NOT simpan expiry di SKU — expiry milik Batch; null = skip engine.

## Verification strategy
- Tests-after: tiap todo punya bun test dan/atau Playwright agent-executable (happy + failure), evidence di .omo/evidence/inventory-userflow-*.(json|png|log), disync di PR yang sama.
- Gate per-PR: `bun run build` exit 0 + `dist/manifest.webmanifest` + `dist/sw.js` ada; `bun test` (unit) hijau; `npx playwright test` untuk todo berlabel e2e; `grep -r "supabase|firebase" src` tetap 0; `grep -q "telegram" src/lib/telegram.ts` ada + tidak ada token plaintext (`grep -r "bot[0-9]" src` 0).
- Final wave F1-F4 paralel, semua APPROVE sebelum handoff.

## Execution strategy
- 8 wave berurutan, 1 wave = 1..6 task, tiap task = 1 branch `feat/<slug>` dari main terbaru (`git pull --rebase origin main` dulu di worktree) + 1 worktree + 1 PR + 1 reviewer + CI hijau + squash merge, sesuai AGENTS.md GitHub Flow + permintaan user tiap task PR dulu. Aturan tabrakan: schema (W1) pemilik src/db/**; guard App.tsx (W2) mendarat dulu, wiring W7 selalu rebase + resolve manual; tidak ada paralel antar-wave.
- Dependency: W0 docs → W1 schema → W2 auth → W3 SKU → W4 inout → W5 expiry → W6 dashboard → W7 setting. Tidak ada paralel antar-wave (schema dipakai semua); dalam wave boleh paralel jika file tidak tabrakan (dicatat per todo).
- Worker mulai via `$start-work inventory-userflow-rewrite` (opsi `--make-pr` per wave).

## Commit strategy
- Format conventional commits per AGENTS.md (feat/fix/docs/test/chore/refactor + scope).
- Tiap todo = 1 branch `feat/<slug>` dari main terbaru + 1 worktree (`git worktree add ../wt-<slug> -b feat/<slug>`), 1 PR GitHub dengan template (FRD trace, apa diubah, QA checklist, evidence path, checklist crew), 1 reviewer, CI hijau, squash merge, hapus branch + worktree, sync .omo di PR yang sama.
